Customer Master Audit

br-ar-customer-master-audit

Audit the Oracle EBS customer master in Excel: duplicate customers (same tax id or same normalised name on different parties), missing payment terms, bill-to sites or address data, credit settings that contradict each other (a credit limit on advance-payment terms, credit check without a limit), inactive parties with active accounts, and, for India, GSTIN and PAN checks (length, format, check digit, state code against the site's state, PAN inside the GSTIN). Lists every finding with its evidence and the proposed correction on an Audit_Findings sheet; changes nothing in Oracle.

When to use

Use when the user asks for a customer master audit, customer data quality, duplicate customers, GST number or PAN validation, or a correction list for the master data team. - customer-audit-findings - party-name-normalisation

# Customer Master Audit (br-ar-customer-master-audit)

> 🚨 **Blitz data = Excel worksheet UDFs, not MCP tools/connectors.** Extract data only by writing `=br_...()` into a cell (via `execute_office_js`) and reading the spill — **never** `tool_search` for `br_*`, **never** `refresh_mcp_connectors`, and never conclude "no Oracle EBS / Blitz connector is set up" (the Blitz Report add-in is an Excel add-in, not an MCP connector, so it never appears in the connector list — its absence there is expected). Load the extraction mechanism first: `read_skill("br-run-reports")`.

> **Performance:** read `br-analytics-standards` at the start of every run. Read
> `references/checks.md` before scoring and `references/customer-audit-findings.md` before writing
> the findings.

Find the customer records that will cause trouble downstream — wrong invoices, tax returns that do
not reconcile, orders released without credit control — and hand over one correction list. You own
orchestration, the checks and the findings; br-run-reports does extraction. **Read-only:** the
corrections the customer upload can make are staged by **br-ar-customer-master-fix** after the user
approves them; everything else goes to the master data team as the list.

## When to use
"Audit the customer master", "find duplicate customers", "check the GST numbers", "customers
without payment terms", monthly master data review, before a migration or a go-live.

## Inputs (ask once, up front, in one question)
- **Operating unit(s)** (required).
- **Checks**: default all generic checks of `references/checks.md`; the India checks when the
  customers are in India or the user asks for them.
- **Policy lists**, only for the checks that need them: the payment terms that mean payment in
  advance (offer the terms found in the data as a list; never guess them from their names), and
  whether every active account must have a collector or a default warehouse.
- **Where GSTIN and PAN are held** when the India checks run: by default the GSTIN in the site's or
  party's tax registration number and the PAN in Taxpayer Id; ask when the data shows otherwise.

## Reports used (authoritative names — do NOT broad-search for them)
| Report (exact name) | Run with | Role |
|---|---|---|
| `AR Customers and Sites` | Operating Unit, Level=Site Use, Show Profile Amounts=Yes, Show Tax Registrations=Yes | one row per site use (and tax registration and profile amount): party, account, site, address, state, statuses, payment terms, credit check and hold, credit limits, collector, warehouse, Taxpayer Id, tax registrations |

Show active only stays at its default (Yes). Several operating units → one run each. Pass the
exact name; fall back to a search only on `#BLITZ_REPORT_NOT_FOUND`.

## Pipeline
1. **Extract — DELEGATE** to br-run-reports. Wait; touch nothing mid-run.
2. **Build the check columns** next to the data on a helper sheet with formulas
   (`references/checks.md`): normalised party name, PAN and GSTIN findings, state code against the
   site's state, missing values, credit consistency. One formula per column, filled down.
3. **Duplicates** on `Duplicate_Groups`: different parties sharing a Taxpayer Id (or the PAN inside
   their GSTINs) or a normalised name; then the near-identical names you find by comparison
   (`references/party-name-normalisation.md`), marked as suspects with their evidence. One party
   with a GSTIN per state is normal and never a duplicate.
4. **Findings** on `Audit_Findings` per the shared contract, one row per finding, `Decision`
   `Proposed`; a `Proposed Value` only where it is derived (the PAN of a valid GSTIN when Taxpayer
   Id is blank) or the user gave it.
5. **Scorecard** on `Customer_Audit` (first tab): per check the severity, the number of findings
   and of accounts; the accounts with the most findings; the share of active accounts clean.
   Cells sharing a format adjacent, one write per block.
6. **Narrative** (≤5 bullets): the worst checks, the duplicate suspects, what the customer upload
   can correct and what goes to the master data team. Offer br-ar-customer-master-fix for the
   approved upload-fixable rows.

## Hard rules
- A finding states its evidence; a duplicate is a **suspect** until a person decides, and merging
  parties is never proposed as an upload fix.
- Never invent a correction value: no payment term, credit limit or tax number that the data or
  the user did not give.
- Policy checks run only with the user's policy; without it they are skipped and said so.
- Analysis only: never write to Oracle and never run an upload from this skill.

## Degradation rules
- No tax registrations in the data (GSTIN kept outside the standard tax registrations, as some
  localisations do) → say the GST checks could not run, and run the rest.
- A state the GST state list does not know → `State not checked`, never a mismatch.
- A very large customer base → run with `Show trx count within x days=365` and audit the accounts
  with transactions first, and say so.

## Talk in the user's language
Customers, accounts, sites, tax numbers and fields — never `br_*` functions or helper sheets.

references/checks.md

# Checks of the customer master audit

Columns are those of `AR Customers and Sites` (Level=Site Use). The report repeats account and
party values on every site-use row: count a party- or account-level finding once per party or
account, a site finding once per site. Inactive rows are out unless a check says otherwise.

## Generic checks
| Check | Severity | Test | Fix Route |
|---|---|---|---|
| Same tax id, different parties | Review | Taxpayer Id equal on two or more Party Numbers | Master data team |
| Same name, different parties | Review | normalised Party Name equal on two or more Party Numbers (`party-name-normalisation.md`); near-identical names found by comparison are listed as suspects with their evidence | Master data team |
| Payment terms missing | Error | active account whose Account Profile Payment Term is blank and whose bill-to site uses have no Site Use Payment Term either | Payment Terms |
| No bill-to site | Error | active account without an active site use whose Site Use is Bill To | Master data team |
| No primary bill-to | Review | active account with bill-to site uses, none of them Primary Flag = Yes | Master data team |
| Address line too short | Error | Address1 shorter than 3 characters on an active site | Master data team |
| Postal code missing | Review | Postal Code blank on an active site, in a country that uses postal codes | Master data team |
| State missing | Error | State blank on an active site in a country with states (India) | Master data team |
| Inactive party, active account | Error | Party Status inactive while Account Status is active | Master data team |
| Credit check without a limit | Review | Credit Check = Yes and no Credit Limit (blank or 0) on the account profile | Credit Limit |
| Limit without credit check | Review | Credit Limit > 0 and Credit Check not Yes | Credit Check |
| Credit limit on advance terms | Policy | Credit Limit > 0 on an account whose payment term is in the user's advance list | Credit Limit |
| Collector missing | Policy | Collector Name blank on an active account (only when the user requires it) | Master data team |
| Default warehouse missing | Policy | Warehouse blank on an active account (only when the user requires it) | Master data team |

A missing value compares as an empty string: test it with `=LEN(TRIM(x))=0`, never `x=""` on a
number column, and score blanks as 0 in any ranking.

## India checks (GSTIN and PAN)
| Check | Severity | Test | Fix Route |
|---|---|---|---|
| GSTIN invalid | Error | GSTIN formula below gives `Length`, `Format`, `PAN entity type` or `Check digit` | Master data team |
| GSTIN missing | Review | active Bill To or Ship To site in India without a GSTIN (the customer may be unregistered; the user decides) | Master data team |
| GSTIN state mismatch | Error | the GSTIN's first two digits differ from the GST state code of the site's State | Master data team |
| PAN invalid | Error | PAN formula below gives `Format` or `PAN entity type` on Taxpayer Id | Taxpayer Id, proposed value the PAN of the party's valid GSTINs when they all carry the same one |
| PAN missing | Review | Taxpayer Id blank | Taxpayer Id, proposed value as above |
| PAN differs from GSTIN | Error | a valid GSTIN whose characters 3 to 12 are not the Taxpayer Id | Master data team (which of the two is right is a judgement) |

GSTIN in A2 (result `OK`, `Missing`, `Length`, `Format`, `PAN entity type` or `Check digit`):
```
=LET(g,UPPER(TRIM(A2)),c,"0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ",
 IF(g="","Missing",IF(LEN(g)<>15,"Length",
 LET(ch,MID(g,SEQUENCE(15),1),cd,CODE(ch),dg,(cd>=48)*(cd<=57),lt,(cd>=65)*(cd<=90),
  pat,{1;1;2;2;2;2;2;1;1;1;1;2;3;2;3},
  okf,AND(IF(pat=1,dg,IF(pat=2,lt,dg+lt))=1,MID(g,13,1)<>"0"),
  IF(NOT(okf),"Format",IF(ISERROR(FIND(MID(g,6,1),"ABCFGHJLPT")),"PAN entity type",
  LET(v,SEARCH(MID(g,SEQUENCE(14),1),c)-1,p,v*IF(ISODD(SEQUENCE(14)),1,2),s,SUM(QUOTIENT(p,36)+MOD(p,36)),
   IF(MID(c,MOD(36-MOD(s,36),36)+1,1)=MID(g,15,1),"OK","Check digit"))))))))
```
PAN in A2 (result `OK`, `Missing`, `Format` or `PAN entity type`):
```
=LET(p,UPPER(TRIM(A2)),IF(p="","Missing",IF(LEN(p)<>10,"Format",
 LET(cd,CODE(MID(p,SEQUENCE(10),1)),pat,{2;2;2;2;2;1;1;1;1;2},
  IF(NOT(AND(IF(pat=1,(cd>=48)*(cd<=57),(cd>=65)*(cd<=90))=1)),"Format",
  IF(ISERROR(FIND(MID(p,4,1),"ABCFGHJLPT")),"PAN entity type","OK"))))))
```
The PAN inside a GSTIN is `MID(g,3,10)`.

references/customer-audit-findings.md

# The Audit_Findings sheet (contract between br-ar-customer-master-audit and br-ar-customer-master-fix)

`br-ar-customer-master-audit` writes it and never changes Oracle. `br-ar-customer-master-fix` reads
it and stages only rows whose `Decision` is `Approved` and whose `Fix Route` it supports. Row 1
holds the headers, data starts in row 2, one row per finding. Find columns by their row-1 header.

| Column | Content |
|---|---|
| Check | the check's name as in the audit's scorecard, e.g. `Payment terms missing` |
| Severity | `Error` (wrong data), `Review` (possibly wrong), `Policy` (breaks a rule the user set) |
| Party Number | the party (registry) number |
| Party Name | |
| Account Number | blank for a party-level finding |
| Site | site number and location, blank for an account- or party-level finding |
| Field | the field the finding is about, e.g. `Payment Terms`, `Taxpayer Id`, `GSTIN` |
| Current Value | the value in Oracle (blank when missing) |
| Proposed Value | only when it can be derived or the user gave it (a PAN taken from a valid GSTIN, a payment term the user named); blank otherwise |
| Evidence | why it is a finding, e.g. `GSTIN 27… is in state 27, the site is in state 24` |
| Fix Route | `Payment Terms`, `Credit Check`, `Credit Hold`, `Credit Limit`, `Order Credit Limit`, `Taxpayer Id` (fixable with the customer upload), or `Master data team` (everything else: addresses, tax registrations, duplicates, statuses) |
| Decision | `Proposed` when written; the user sets `Approved` (with a `Proposed Value`) or `Rejected` |
| Result | written by br-ar-customer-master-fix only: `Updated` or the error message |

Profile fields (`Payment Terms`, `Credit Check`, `Credit Hold`) and profile amounts (`Credit Limit`,
`Order Credit Limit`) are fixed on the account profile; a site-level finding of those fields goes
to `Master data team`.

# Normalising a party name for comparison

Two names are the same party name when their normalised forms are equal. The formula (Excel 365,
the name in A2) upper-cases the name, cuts it at `(FORMERLY`, `(FORMALLY` or `(EARLIER`, removes
`M/S`, turns `&` into `AND`, drops apostrophes, turns `. , - / ( )` into spaces and drops the
legal-form words:

```
=LET(s," "&UPPER(A2)&" ",
 t,IFERROR(TEXTBEFORE(s,{"(FORMERLY","(FORMALLY","(EARLIER"}),s),
 r,{" M/S."," ";" M/S "," ";"&"," AND ";"."," ";","," ";"-"," ";"/"," ";"("," ";")"," ";"'",""},
 c,REDUCE(t,SEQUENCE(ROWS(r)),LAMBDA(a,i,SUBSTITUTE(a,INDEX(r,i,1),INDEX(r,i,2)))),
 w,TEXTSPLIT(TRIM(c)," "),
 k,FILTER(w,ISNA(XMATCH(w,{"PRIVATE","PVT","LIMITED","LTD","LLP","MS","MESSRS","THE","CO","COMPANY","CORPORATION","CORP","INC"})),""),
 TEXTJOIN(" ",TRUE,k))
```

Examples: `M/S. Vision Electricals Pvt. Ltd.` → `VISION ELECTRICALS`; `Acme Cables (India) Pvt. Ltd.`
→ `ACME CABLES INDIA`; `A&B Traders Co.` → `A AND B TRADERS`.

- INDIA stays in the name: it often tells two companies apart.
- Two different parties with the same normalised name are never a match for each other; they are
  candidates (in a duplicate check, a duplicate suspect).
- Beyond equal names, compare the remaining ones yourself: shared distinctive words (not a city,
  not a common word like INDUSTRIES or TRADERS), initials written out (`A B C` and `ABC`), a group
  name with a division. Claude may score them in script: word overlap as 2 × shared ÷ (words of A
  + words of B), and character similarity; 0.90 and clearly ahead of the next name is a
  suggestion, 0.75 a candidate. Copilot compares the lists itself. A suggestion is shown with its
  evidence and confirmed by the user, never applied on its own.
