# Upload API Patterns

Module-specific API facts. General rules are in `upload-development` skill.

## General

- Never direct DML on application base tables; interface tables are the exception. Highest-level public API first (`*_PUB`/`*_API`/`*_GRP` → interface + concurrent program → `*_PKG`); supplement with targeted updates only for fields the API cannot set.
- Value→id mapping belongs in the LOV/`VALUE_TO_ID_QUERY`, never in PL/SQL.
- Combine entities the user enters together into one upload; process a repeating parent once (uploads run top-down).

## ONT Order (`XXEN_ONT_UPLOAD`, + `_11I`)

A line split goes through `oe_order_pub.process_order` in one call: the original line as an update and each new shipment as a create with `split_from_line_id`, all carrying `split_action_code='SPLIT'` and `split_by='USER'`. `OE_SPLIT_UTIL.Check_split_Course` rejects the call unless the original's new quantity plus the new shipments equal its current quantity (`OE_INVALID_SPLIT_QTY`), and a split needs no change reason on a booked line although a plain quantity decrease does. `OE_SPLIT_UTIL.Default_Attributes` rebuilds each new shipment from the original line and keeps only its quantity, plus request date, warehouse and ship to when `split_request_date`/`split_ship_from`/`split_ship_to` are `'Y'`; those three flags exist on every R12 level but not on 11i, where a new shipment takes only its quantity. The upload maps returned line ids back to rows by table index, never through `orig_sys_line_ref`, which the api copies from the original line onto a split and which is the order's own source reference.

A line price adjustment is passed to `oe_order_pub.process_order` through `line_adj_tbl`. A record left at `oe_order_pub.g_miss_line_adj_rec` because the modifier lookup found nothing is rejected by `OE_VALIDATE_LINE_ADJ` with `OE_ATTRIBUTE_REQUIRED` / token `List_header` (`list_line_type_code not in ('COST','TAX') and list_header_id is null`) — resolve the modifier line before building the record and error the row yourself when it does not resolve. Take `list_line_type_code` from `qp_list_lines`, never hardcode `'DIS'`: the Discount Modifier LOV offers surcharge lists (`list_type_code in ('DLT','SLT')`), whose lines are `SUR`, and the download subqueries read adjustments back with the same set. Back-calculating a `%` operand from a typed selling price divides by the unit list price, so a zero list price is a validation error, not a guard.

The customer contact (`sold_to_contact_id`) is a contact record (`hz_cust_account_roles`), not a person: a person who is a contact at account level and at a site has two records sharing one name and one `hz_org_contacts.contact_number`, and the contact number can be null. `header_val_rec.sold_to_contact` resolves the name with `rownum=1` and is converted only when `<> fnd_api.g_miss_char` (`OE_HEADER_UTIL.Get_Ids`), so a blank never clears it: set `sold_to_contact_id` directly. `line_rec.override_atp_date_code` (`'Y'` or null) needs profile `OM: Authorized To Override ATP` (`OE_SCH_OVER_ATP_NO_AUTH`), a schedule ship date or scheduling action on the line (`OE_SCH_OVER_ATP_NO_SCH_ACT`), and is refused on service, return, drop-ship and quote lines; clearing it reschedules the line with an availability check, which can move the schedule ship date. Both exist on 11i.

`oe_order_pub.process_order` returns S with warnings left on its message list, among them the duplicate customer PO check (`OE_VAL_DUP_PO_NUMBER`, profile `ONT_ENFORCE_DUP_PO`) and credit check holds, so the upload appends that list to its success message; the message type cannot separate warnings from notes (the duplicate PO message has none, credit holds are `NOTE` like "Order has been booked."). Call it with `p_init_msg_list` true: the list is not cleared between calls, so every later order of an upload would otherwise report the earlier orders' messages too.

A salesperson is valid for an order when it is date-effective in the operating unit: the Sales Order form's list (`ra_salesreps`) and `OE_VALIDATE.salesrep` test `start_date_active`/`end_date_active` and ignore `jtf_rs_salesreps.status`, which is null or `I` on many records. Filter salesperson lists by the dates, never by status. Names repeat (an end-dated and an active record can share one); `oe_value_to_id.salesrep` then takes the date-effective one.

## OTL Timecard (`XXEN_OTL_UPLOAD`)

`hxc_time_building_blocks` is one versioned self-referencing table (TIMECARD→DAY→DETAIL, latest = `date_to=31-DEC-4712`); attributes via `hxc_time_attribute_usages` (Projects: category `PROJECTS`, a1 project_id, a2 task_id, a3 expenditure type NAME; Payroll: category `ELEMENT - <element_type_id>`); never author SECURITY attributes. Status = `hxc_timecard_summary.approval_status` (`HXC_APPROVAL_STATUS`, view_application_id 3). Transferred = `hxc_transactions`/`_details` SUCCESS rows. Create: `hxc_timestore_deposit.create_time_entry` → `create_attribute` (`'Dummy Element Context'` = `'ELEMENT - '||id`) → `execute_deposit_process('SAVE'|'SUBMIT','OTL Deposit Process')` (no commit, clears collections). Update: `get_timecard_tables` → `update_building_block`/`update_attribute`; never `delete_detail_bb` when batching (it reloads from DB, wiping pending edits) — mark `date_to`/`new='N'`/`changed='Y'` on the loaded collection. `delete_timecard` is immediate. Errors via `translate_message_table(convert_to_dpwr_messages(p_messages))`. Projects validation uses the SESSION OU; time-entry rules fire at SUBMIT. Eligibility `hxc_preference_evaluation.resource_preferences(...,'TS_PER_APPLICATION_SET',...)`. `full_name` can be ambiguous — require employee number. Write ids back to `_chr` shadow columns.

## FND Responsibility (`XXEN_FND_UPLOAD.create_update_responsibility`)

Row types: Responsibility (`FND_RESPONSIBILITY_PKG.INSERT_ROW/UPDATE_ROW`, then `resp_synch`; UPDATE_ROW is a full-row write — gate on a real change) and Menu/Function Exclusion (`FND_RESP_FUNCTIONS_PKG`, key app+resp+rule_type+action_id, add idempotent). Business key = Application + Responsibility Key. `VERSION` 4/W/M (labels hardcoded, no lookup). Request Group needs `request_group_id`+`group_application_id` (id alone not unique). No delete — end-date. Multi-entity UNION filters: primary row on `1=1` + sub-row on `2=2`. Assignment `FND_FNDSCRSP`. Linter I7 flags only non-Function assignment levels.

## FND Profile Option Values (`XXEN_FND_UPLOAD.upload_profile_option_value`)

- `xxen_util.profile_option_value_sql` turns `fnd_profile_options.sql_validation` into a select of `profile_option_value` and `visible_option_value`; the display function, the upload list of values (`profile_option_value_lov`) and the value resolution all use it. Validations needing the profile form's context (`:PROFILE_QF.*`, `:LEVEL_CONTEXT.*`) or binding the entered value (format checks) yield no list, so the value is saved as entered.
- Id-list validations return the stored value as a NUMBER (`MO: Operating Unit` selects `organization_id`): compare `to_char(x.profile_option_value)` with a text value, or the comparison raises `ORA-01722`.
- `fnd_profile.save` returns false for a level the profile's hierarchy type or enabled flags do not allow, and a null value deletes the row. The server and responsibility hierarchy (`SERVRESP`) stores both levels at 10007: a responsibility value with `level_value2` -1 or the server node, a server value with `level_value` and `level_value_application_id` -1.

## HR

- Assignment update: `update_emp_asg` → re-query the object version number (OVN) → `update_emp_asg_criteria`. `primary_flag` not updatable. `hr_positions_f` (not `_vl`). Person queries datetracked on `sysdate`.
- Organisation: `create_hr_organization`, `update_organization`, `create_org_class_internal` (not `create_org_classification`), `enable/disable_org_classification`, `create/update_org_information` (update blocked for Business Group Information etc.).
- Person EIT (`XXEN_PER_UPLOAD.create_update_person_eit`): API `hr_person_extra_info_api`; types/segments live under DFF **`Extra Person Info DDF`** (context column `PEI_INFORMATION_CATEGORY`, `pei_information1..30`), not `PER_PEOPLE_EXTRA_INFO`. Segment columns call `xxen_util.dff_attribute_lov(800,'Extra Person Info DDF',:$column$.information_type,'PEI_INFORMATIONn',...)` directly; `validate_dff_attributes('PER','Extra Person Info DDF','V','I')`. COMMENTS bounded to the filtered context (the all-contexts `listagg` overflows at 176 contexts). `employee_number` unique only per business group. An EIT invisible in the People form is responsibility security (`per_info_type_security`), not a bug.
- Person Extra Information LOV context: `l_context_code` declared `descriptive_flex_context_name%type` (an unresolved >30-byte context aborted the whole upload with `ORA-06502`).
- A person's types are the rows of `per_person_type_usages_f`; `per_all_people_f.person_type_id` of a contingent worker is the generic `OTHER` type (External), so a filter or display on it drops or mislabels every contingent worker. Pick one usage per person by system type priority (EMP, CWK, APL, EX_EMP, EX_CWK, EX_APL), as `XXEN_PER_UPLOAD.create_update_person` does.
- `hr_assignment_api.update_emp_asg` (12.1.3) ignores `p_concat_segments`: the soft coded flexfield change is silently dropped while the call succeeds. Select or create the combination with `hr_kflex_utility.ins_or_sel_keyflex_comb('PER','SCL',<pay_legislation_rules rule_type 'S'>,p_concat_segments_in=>...)` and pass `p_soft_coding_keyflex_id`. `update_emp_asg_criteria` does honour `p_concat_segments` for the people group.
- Concatenated key flexfield values passed to the HR apis (`'V'` mode) hold the DISPLAYED segments only. `pay_people_groups.group_name` and `hr_soft_coding_keyflex.concatenated_segments` are written when a combination is created and go stale when the structure changes later (most Vision people groups), so re-sending a stored string can fail with `FLEX-MISSING CONCAT VALUES`.
- HR flexfield errors raise `ORA-20001: FLEX-<NAME>: N, <token>, ..., N, ERRMSG, <text>` with `hr_utility.get_message` empty; the row message is the text after `ERRMSG, `.

## PO

- Receiving interface: `pie.interface_line_id=rti.interface_transaction_id`; `org_id` required on both interface tables (else RVCTP silently skips); `RVCTP` args `('BATCH',group_id,org_id)`; `auto_transact_code='DELIVER'`; receiving subinventory/deliver-to come from `po_distributions_all`.
- Purchasing Document (`XXEN_PO_UPLOAD`): new lines → PDOI; existing Standard PO edits/splits/header-only → `po_document_update_grp.update_document`, gated on `l_interface_line_id is null` (not `l_po_line_id`). "Cannot be changed" checks use `value_changed` (a copy-pasted split flags every cell), falling back to `value_modified` when the distribution cannot be resolved. Seeded object types (`po_pub_*_rec_type`) gain attributes across patch levels: construct an empty instance dynamically from the `all_type_attrs` count (`pub_null_args`) and set fields by name; never positional constructors.
- Ship-to and deliver-to location LOVs filtered by inventory organization must keep the shared locations (`hr_locations.inventory_organization_id` null, the majority on most sites): the PO form and PDOI accept a location when `nvl(inventory_organization_id,ship_to_org)=ship_to_org`. Ship-to additionally requires `ship_to_site_flag='Y'` and lists every ship-to location while the ship-to organization is blank; deliver-to has no flag check and lists nothing without an organization. Both exclude inactive locations. Reference: the two LOVs of the PO Purchasing Document Upload and `PO Requisition Deliver To Location (active)`.
- Requisition Import writes `SQL Error In Account Generator wf` into `po_interface_errors` (with a follow-on `PO_RI_INVALID_CHARGE_ACC_ID`, "Charge account is invalid") whenever the PO Requisition Account Generator raises anything at all: `POR_UTIL_PKG.req_imp_act_up_frm_wf` holds the generator's message in a `varchar2(50)` local, and `interface_start_workflow` assigns the decoded FND message into that `in out nocopy` formal, so any message over 50 bytes dies as ORA-06502 in the same `when others`. The real reason is only recoverable by replaying the interface row through `por_util_pkg.interface_start_workflow` with a wide `fb_error_msg`, or by keying the line in the Requisition form, which reaches the same workflow through `PO_ACCOUNT_HELPER.req_build_accounts` with a `varchar2(2000)` buffer and shows the message. The generator only runs for interface rows whose charge account segments are ALL null, so supplying the segment columns bypasses it.
- `por_util_pkg.interface_start_workflow` takes 102 arguments on 12.1.3 and 103 on 12.2 (`P_MISC_LOA`, no default), so a static call compiles on one release only. Build the call dynamically and append `p_misc_loa=>null` when `user_arguments` reports it; declare the `in out` formals inside the dynamic block and bind only the inputs and the outputs you read.
- `po_headers_interface.supply_agreement_flag` does not exist on 12.2.4 (`po_headers_all` has it). Set it only through the dynamic update after the header insert, which errors the row on `-904`. Never add it to the static insert or to the Error SQL.

## WIP (`XXEN_WIP_UPLOAD`)

`wip_interface_errors.error` (type 1 = error); `load_type` 1/4/3 encodes job type; lookups `WIP_DISCRETE_JOB`/`WIP_JOB_STATUS` app 700; numeric flags via `BOM_SYS_YES_NO` (1/2). Mass Load update null handling: most columns `nvl(new,old)` (cannot clear); `schedule_group_id`, `build_sequence`, completion sub/locator, `attribute1-15` accept `g_miss_*` to clear; project/task gated on project. On create they must never receive `g_miss_*`: Mass Load stores the sentinel literally (9.99e125 lands in `wip_discrete_jobs.schedule_group_id`/`build_sequence`) and the ASCP Memory-Based Snapshot then fails with `ORA-01455: converting column overflows integer datatype` in `mslsnj_snp_jobs`, whose log blames an unrelated `msc_plan_buckets` statement. Non-standard jobs without assembly/routing cannot be updated (`reexplodeJob` returns U). `allow_explosion='N'` on updates; for creates detect routing/BOM existence to choose `substitution_type` 3 vs 2, default `'Y'` only for header-only creates. Change records on routing-derived operations are dropped on Create+explosion. Pre-validate resource–department. Post-procedure cascades errors per job, cleans interface rows, allocates `group_id` from `wip_job_schedule_interface_s` per org (`g_miss_num` placeholder + `request_id` scope), stamps `source_code='BLITZ:'||request_id`/`source_line_id=upload_row` for post-WICMLP linkage, updates `xu.job_name` for all creates; `request_id_` = the upload request. Phantoms excluded (`wip_supply_type<>6`).

## CST cost import (`XXEN_CST_UPLOAD`)

`CSTPCIMP` selects by GROUP ID only and stamps its cost-type parameter on every row — one group per (run, cost type): row proc stamps `group_id=conc_request_id`, post proc re-stamps `cst_lists_s.nextval` per cost type; skip the import when nothing was staged. Delete-successful-rows leaves errors with `error_flag='E'`; hidden in/out `ROW_ID` joins the error result and updates in place on re-upload. Org LOVs filter `cost_organization_id=organization_id` and non-process orgs. `BASED_ON_ROLLUP` defaults Yes when shrinkage ≠ 0 (import rule). Mode 1 insert / 2 replace per item. DFF via `validate_dff_attributes('BOM',...)`. Resource rates: `cost_element_id in (3,4)`, `functional_currency_flag<>1`; overhead (option 3) serves both dept and resource interfaces, dept duplicate key excludes basis; associations `cost_element_id` 3/4 with overhead 5 or 2. Deletes are direct (`cst_resource_costs`) or table handlers (`CST_DEPARTMENT_OVERHEADS_PKG`/`CST_RESOURCE_OVERHEADS_PKG.Delete_Row`), resolved by natural key, refused for frozen/non-updateable cost types; Success SQL restores per-row delete messages (`case when xu.delete_col is not null`) and null-safes the interface-error exclusion. Zoom assignments target the launching form function (never `_UPDATE` test functions), only cost-type-bearing blocks, mapping the form's cost type to BOTH Target and Source Cost Type. `RESOURCE` is reserved (`RESOURCE_CODE`). Cost migration: point the rollup cost type's Default Cost Type at itself while purging/re-uploading, or the rollup back-fills from the default.

## INV

- Stock Locator: `inv_loc_wms_pub.create/update/delete_locator`; build `l_disabled_date` case-by-case (`g_miss_date` trips the disable check). `process_kff_combination_1('ALL')` returns the escaped concat (`\`→`\\`, delimiter → `\delim`), `'<N>'` the raw segment; `_kfv.concatenated_segments` is raw; decode with `kff_segment_dsp`. PJM projects via `pjm_projects_all_v`+`pjm_project_parameters`.
- Item revisions: stage in `mtl_item_revisions_interface` (same INCOIN run); clear with `'!'`, null = no change (API and interface); local `value_changed` honours `p_upd_on_cre_null_mode`; a revision recurring across cross-product rows is processed once (`g_item_tbl('R:...')`); Success SQL sources bare `mir.col` (custom Error SQL, no delete). Revision DFF `MTL_ITEM_REVISIONS` (app 401, 15 attrs) via `mtl_item_revisions_vl`. Never use the mode-blind package `get_new_value` for the revision merge.
- Cross Reference: `MTL_CROSS_REFERENCES_PUB.PROCESS_XREF` (CREATE/UPDATE/DELETE, id mandatory for update/delete); NULL clears on update (`new_value` contract fits exactly — no nvl guard); read old description from `_vl` (`_b` goes stale). Field applicability mirrored in `validate_item_xref_row` (org vs applicable-to-all, UOM only for the GTIN type, revision needs org). Resolve the item at its master org. `ORA-01416` in a Success SQL = self outer join from mechanical `(+)`. Assignments `INV_INVIDXRT`, `ENG_INVIDXRT`, `INV_INVIDITM`, `INV_INVIDITM_ORG`.
- Item categories in an assigned organization: Item Import copies the master organization's assignment into a newly assigned organization only for **default** category sets (`mtl_default_category_sets`), and as a point-in-time copy of the master's category at that moment, never refreshed afterwards. A user-defined set is never propagated, so `Assign To Organizations` stages its own `mtl_item_categories_interface` CREATE row per organization for org control level sets (`mtl_category_sets.control_level=2`); a master controlled set is held once on the master organization and needs none. An explicit row for an org controlled default set does not collide with Item Import's own defaulting in the same process set.
- Transaction Upload: for source type 3 (Account issue/receipt) `mtl_transactions_interface.transaction_source_id` is the distribution account ccid and the transaction manager rejects segments without it (`Invalid transaction source segments`); Account Alias is a GL shorthand alias (`fnd_shorthand_flex_aliases`) that only defaults the Distribution Account, so validate the Distribution Account, not the alias. Source type 6 (Account alias issue/receipt) takes its alias (`mtl_generic_dispositions`) through Transaction Source.
- Transaction Upload quantity sign: `mtl_transactions_interface.transaction_quantity` must be negative for issue from stores (`transaction_action_id` 1) and for Intransit Shipment (21), and `upload_inv_trx` writes `-abs(...)` for both on the transaction and on the lot line, so the user may enter either sign. Every other action reaches the interface as entered; a wrong sign there surfaces as `Transaction quantity has an incorrect sign for the given transaction action`. A Transportation Account that is not the freight code's own `org_enabled_freight_val_v.distribution_account` is rejected with `The transportation account is not valid for the given freight code`, and most Vision freight codes have none.
- Locator control is a three-level hierarchy, never an item attribute on its own: `decode(mtl_parameters.stock_locator_control_code,4,decode(mtl_secondary_inventories.locator_type,5,mtl_system_items_b.location_control_code,mtl_secondary_inventories.locator_type),mtl_parameters.stock_locator_control_code)`. Org holds 1/2/3/4 (4 = defer to subinventory), subinventory 1/2/3/5 (5 = defer to item), item 1/2/3; effective 2 or 3 means a locator is required, 1 means the field is disabled. So a prespecified-locator item in a subinventory with no locator control needs NO locator, and testing only the item's `location_control_code` rejects rows the form accepts. Oracle's own copies of the rule: `inv_material_status_grp.get_locator_control(p_org_id,p_inventory_item_id,p_sub_code)` (R12 only, absent on 11i, and its `when others` returns 1 so a bad subinventory silently reads as "no control") and `mtl_inv_validate_grp.locator_control`, which additionally collapses 3 to 2 under `no_neg_balance` - irrelevant when the question is only whether a locator is required. `XXEN_INV_UPLOAD.locator_control` is the in-package helper; evaluate the To-Locator of a transfer against the DESTINATION organization and subinventory, not the source.
- Item Upload: an item attribute whose control level is Master (Item) is silently dropped when the row targets a CHILD organization - `set_item_att` returns false, so the value never reaches the interface and `g_entity_changed_flag` stays unset; a row changing only such attributes reports no change rather than an error. Updates only: a create with a non-null value is always taken. The master-controlled set is built at runtime by `populate_master_attribs_table` from each column's COMMENTS query over `mtl_item_attributes.control_level`, so it follows the site's Item Attribute Controls setup - the same attribute can be org-controlled on one instance and master-controlled on another, and a fixed list must never be assumed.
- Item Upload automatic numbering: a blank Item takes its number from `XXEN_UPLOAD_CUSTOM_EXTENSIONS.inv_next_item_number` first, then (R12 only) from `EGO_ITEM_PVT.Get_Seq_Gen_Item_Nums` when the nearest catalog up the hierarchy whose `item_num_gen_method` is not `I` is `S` (sequence generated: prefix || sequence || suffix, skipping numbers already used). INCOIN never generates these itself: Product Hub numbers items only in its own import, where `EGO_IMPORT_UTIL_PVT.Preprocess_Import` runs the item interface with `default_flag` 2 (`INVPAGI2.assign_item_header_recs`), and that step matches rows on `source_system_id`, which upload rows leave blank. Function generated (`F`) numbers run in the Java import program from Product Hub user-defined attributes, so the upload cannot support them. A master-org create in a catalog whose inherited `new_item_request_reqd` resolves to `Y` is rejected first (R12 only): Item Import (`INVNIRIS.mtl_validate_nir_item`) would create it unapproved as a Pending engineering item that Master Items cannot query, failing its category and child-org assignments with no `mtl_interface_errors` rows. 11i Item Import has no such step.
- Lot Upload (`upload_lot`): decision: create through `inv_lot_api_pub.create_inv_lot` and update through the table handler `mtl_lot_numbers_pkg.update_row`, as the Lot Numbers form (INVTDILT) does. `update_inv_lot` omits `description`, `curl_wrinkle_fold` and `vendor_id`, skips the global lot attribute propagation (profile `INV_GLOBAL_LOT_ATTRIBUTES`) and applies `expiration_date` only for shelf life codes 2 and 4 with null meaning keep; the handler writes the status and grade history itself, so the upload performs the form's validations before calling it.
- `create_inv_lot` with `p_source=>inv_lot_api_pub.inv` and full validation rejects every shelf life days item whose derived expiry is not `sysdate+shelf_life_days` (`INV_EXP_DATE_NOT_CONSIDER`), i.e. any lot with an origination date other than today. The OSFM sources skip that check; `osfm_form_validate` keeps the `Populate_Lot_Records` item and parent defaulting and the remaining validation.
- The `Lot Attributes` flexfield (application 401, context `LOT_ATTRIBUTE_CATEGORY`) maps segments to named `mtl_lot_numbers` columns (`COLOR`, `VOLUME_UOM`, `DESCRIPTION`, ...) as well as `C_/N_/D_ATTRIBUTEn`. `xxen_util.dff_attribute_value_to_id` resolves only the numbered columns; `inv_lot_api_pub.wms_lot_attr_validate` validates the stored values of all of them.

## WSH Pick Confirm (`XXEN_WSH_UPLOAD`)

Rows are pick allocations (`mtl_material_transactions_temp` keyed by `transaction_temp_id`), one per lot (`mtl_transaction_lots_temp`), joined to the delivery line by `move_order_line_id`. No Create mode: a Yes parameter pre-flags downloaded rows (`:confirm_all`), a second one (`:ship_confirm`) rides along as a hidden column into the post procedure. The row procedure only validates, creates a new LPN (`wms_container_pub.create_lpn`, context pregenerated; existing LPNs accepted only in context 5 or 11) and stages the row's values in a package-global table keyed by task; the post procedure runs once per task over those globals, so a sibling lot row in error blocks the whole task. Confirm sequence: `inv_mo_line_detail_util.query_rows(p_line_detail_id)` -> set quantities, subinventory, locator, staging location and `transfer_lpn_id` -> `inv_mo_line_detail_util.update_row`; lots replaced wholesale with `inv_trx_util_pub.delete_lot_ser_trx` + `insert_lot_trx` (a function returning the row id, error text in `x_proc_msg`); then `inv_pick_wave_pick_confirm_pub.pick_confirm` (move order type `inv_globals.g_move_order_pick_wave`, transaction mode 1, `inv_trolin_util.query_rows(p_line_id)` for the line table). Serial controlled items (control codes 2 and 5) are rejected. Pick confirm splits the delivery detail per lot and keeps the short-pick remainder on the ORIGINAL detail id as backordered; the confirmed material transactions get NEW ids (an issue/receipt pair, `transaction_action_id=28`, quantities negative on the issue side), so the Success SQL joins the latest negative row by `move_order_line_id` + source subinventory + locator (`mtl_material_transactions_n17`) and lots via `mtl_transaction_lot_numbers`. Ship confirm `wsh_deliveries_pub.delivery_action('CONFIRM')` only when no line of the delivery is still in `R`, `S` or `N` (backordered `B` lines are unassigned and do not block); action flag `S` (ship unspecified quantities): a non-WMS pick leaves `shipped_quantity` null and flag `B` backorders the staged line, while a WMS pick fills it. The API returns `W` for the OTM outbound-interface notice on Vision; treat `W` as success and append the text. `pick_confirm` accepts an over-pick (6 of 5) and ship confirm then fails on the over-ship tolerance with the line stuck as over-picked, so reject a picked total above `mtl_txn_request_lines.quantity-quantity_delivered` before touching the allocation. A row pre-flagged by the Confirm All parameter is processed only once its status is `Valid` (the add-in validates on upload); a programmatic test file must set Status/Message itself.

## WSH Container Items (`XXEN_WSH_UPLOAD.upload_container_item`)

## EAM

Assets are CSI instances (`EAM_ASSETNUMBER_PUB`), linked to FA via `csi_i_assets`; asset groups/activities/rebuildables are `mtl_system_items_b` with `eam_item_type` (use INV Item Upload); asset BOMs via BOM Bill of Materials Upload. PM schedules are written as the Preventive Maintenance form (EAMPMDEF) writes them, never through `EAM_PMDef_Pub.Create_PM_Def`/`Update_PM_Def`: those overwrite every header column from the record, recreate the activities without their next service dates and the rules under new ids (11i: a null `rule_id` and `last_service_reading`), and 11i rewrites `created_by`/`creation_date`. The form inserts and updates `eam_pm_schedulings`, `eam_pm_activities` and each rule by `rule_id` through its own table handlers, then (ON-COMMIT) validates the posted rows with `validate_pm_header_and_rules` and, on R12, `validate_pm_activities`, and calls `update_pm_last_cyclic_act` and `update_pm_last_service_reading`; 11i only validates. It never writes the header's `activity_association_id` or `day_tolerance` (R12), `current_wo_seq`, the next service dates or a rule's `last_service_reading`, and a new schedule starts at `current_cycle` 1, `current_seq` 0. The schedule name is unique (`EAM_PM_SCHEDULINGS_U2`). Read the form logic from `$AU_TOP/resource/EAMPMDEF.pll` (`frmcmp_batch module_type=library script=yes`) and the triggers from `frmf2xml` of the fmb; users run `XMLSG` after. INV org context via `fnd_profile.put('MFG_ORGANIZATION_ID',...)`. `csi_counters_tl` for names; `mtl_eam_locations.start_date/end_date`; failure code tables have no org_id; no `Delete_FailureSet`/`Delete_ItemActivity` (end-date). Asset Number Upload: read-only context columns from `mtl_eam_asset_numbers_all_v` (`maintenance_object_id`). `eam_assetnumber_pub.update_asset_number` renames an asset when `p_instance_id` identifies it and `p_instance_number` carries the new number (Oracle rejects a number in use), so the upload finds an existing asset by its Asset Id, trusted on Update only; a copied row with the id creates a new asset. Its `p_location_type_code`/`p_location_id` set the current location: the 12.2 Update Asset page and the create API offer `hz_locations` only (type `HZ_LOCATIONS`), the API refuses the change for an asset located in inventory (`EAM_INVALID_LOCATION_UPDATE`), and nothing clears a location. The 11i API has neither argument and the 11i asset number is the serial number, so the twin keeps both read only. The parent asset is a `mtl_object_genealogy` link of genealogy type 5 between the assets' `mtl_serial_numbers.gen_object_id` (the view's `gen_object_id` and `parent_gen_object_id`); the asset APIs have no parent argument, so maintain it with `inv_genealogy_pub` (object type 2, origin 3): `update_genealogy` end-dates the open link (name `p_org_id` to select that overload) and `insert_genealogy` adds the new one with a start date later than that end date, which the API otherwise rejects as an overlap; it also rejects the asset itself or one of its descendants as parent (`INV_EAM_GENEALOGY_LOOP`). `csi_ii_relationships` is not involved, and the standard hierarchy page writes no asset log entry. Asset attribute values (the attribute groups of an asset or rebuildable number; DFF `MTL_EAM_ASSET_ATTR_VALUES`, application 401, columns `C_ATTRIBUTE1-20`, `N_ATTRIBUTE1-10`, `D_ATTRIBUTE1-10`) go through `eam_assetattr_value_pub.insert_assetattr_value`/`update_assetattr_value`, identical 57 arguments on 11i: pass item, serial and `p_creation_organization_id` (no maintenance object) plus the `association_id` from `mtl_eam_asset_attr_groups` (item, org, context). The API validates the segments in id mode, so translate the character display values with `xxen_util.dff_attribute_value_to_id` first and pass number and date columns typed. There is no delete API. On 11i the API additionally checks the organization through `eam_common_utilities_pvt.verify_org` against the hard-coded responsibility 20539 (Oracle Inventory, application 401) and `wip_eam_parameters`; without that organization access every row fails with `Creation organization Id invalid`.

## OPM (`XXEN_OPM_UPLOAD`)

Upper-case document numbers. Per-procedure `api_version` (formula/recipe header 1; formula detail, recipe vr/routing steps/orgn ops/resources 2). `gmd_recipe_detail.recipe_dtl` fields: `usage_uom`, `process_um`, `oprn_line_id`, `routingstep_id`. Operation line = `gmd_operation_activities.oprn_line_id` by routing step + activity. `create_recipe_mtl` is insert-only — step/material association edits are base DML (documented). Token names in GMD messages can be misleading — read the `IF` above the `SET_TOKEN`. Routing updates need an OPM responsibility with org access (`GMD_ROUTING_INVALID`/"does not have access to organization" is security, not a bug); dependency inserts need `routingstep_no_uom` from the dependent step's operation. 12.2.4 lacks `fm_rout_dtl.oprn_yield`/`recipe_yield` (accepted drop).

## BOM Standard Operations (`XXEN_BOM_UPLOAD.upload_std_op`)

Table handlers only (`bom_std_op_pkg`/`bom_std_op_res_pkg`, direct DML for substitutes); row-by-row with `g_last_*` cache. Bucket from `(line_id presence, operation_type)`: STD (standard routing operation, no line) / FLE (flow line event) / FLP (flow line process) / FLL (flow line operation). Existence id-first; three hidden rowid round-trips; two savepoints. Applicability gate `validate_std_op_excel_row` (client + server backstop; accumulates failures space-joined): Value Added/Critical → FLE; Count Point/Autocharge/Backflush/Check Skill → STD; Display Sequence editable FLP/FLL; resources not FLP/FLL, substitutes not FLE; Replacement Group required for substitutes, forbidden on primaries; subinventory/locator, yield, mandatory flags, track dates → STD + WSM org; Shutdown → STD + eAM; Task Type → WMS installed (`mfg_lookups WMS_TASK_TYPES`, never a value set). The five WSM flags (Operation Yield Enabled, Use Org Settings, Show Next Op, Show Scrap Codes, Show Lot Attributes) default Yes for all types and are editable only in a WSM org (`applicable_flag_code`); standard-op flags default Yes, editable only in their bucket; `count_point_type` composed from Count Point+Autocharge. Department read-only except FLP/FLL; Operation Type null = Event (`nvl(...,1)`); rename detection explicit; Schedule defaults No; substitute-group delete cascades only when no other primary uses the group. Download params: Organization Code (bind), Manufacturing Mode (matching value), Operation Type, Operation Code (grouped LOV), Department, Contains Resource (operation-level `in (select ...)`, still multi-select).

## FA

- Mass Additions (`XXEN_FA_UPLOAD.create_update_mass_addition`): targeted `UPDATE fa_mass_additions SET <changed cols>` (never `FA_MASSADD_PREPARE_PKG.update_mass_additions` — full-row `SET ROW` replace); Split/Unsplit via `SPLIT_MASS_ADDITIONS_PKG`; Create = controlled insert (`FA_MASS_ADDITIONS_S`, `feeder_system_name='BLITZ UPLOAD'`) then UPDATE the trigger-created `fa_massadd_distributions` row (never insert a second); Merge Group + Primary Line + Sum Units (order-independent); match by hidden id else business key, ambiguity errors; Split/Merge/Add-to-Asset only on NEW/POST/ON HOLD; Queue = `fa_lookups QUEUE NAME`; Asset Type meaning from `fa_lookups`.
- `fa_mass_additions.depreciate_flag`/`amortize_flag` hold `YES`/`NO` (`fa_lookups YESNO`), not `Y`/`N`: Post Mass Additions rejects a `Y` with `Depreciate flag &DEPRECIATE_FLAG must be YES or NO`.
- The mass addition `attribute_category_code`/`attribute1-30` are the asset DFF `FA_ADDITIONS` (not the `FA_MASS_ADDITIONS` DFF on `CONTEXT`). Its context is the category's concatenated segments (context not user-overridable); `FA_ADDITION_PVT` defaults it from the category when null and nothing on the post path validates the values, so the upload derives the context from the category and validates with `validate_dff_attributes('OFA','FA_ADDITIONS','V','I')`. `display_flexfield_value` must get the value via `p_value`, since the DFF's table is `FA_ADDITIONS_B`.
- The Queue column displays blank on the development instance (`xxen_util.meaning` finds no `QUEUE NAME` rows) and that is what keeps unchanged rows uploadable: the Queue list offers only Post/On Hold/Delete/On-Review, so a displayed `New` fails id translation (`Queue is invalid`) on every downloaded row. The 11i twin shows the `fa_lookups` meaning and has that failure.
- Asset Upload: DFF via `asset_cat_rec.desc_flex` (never `global_desc_flex`, varchar2(30)); `update_desc` replaces both flex records wholesale (pass current values for uncarried attributes); `depreciate_flag` change is its own `do_adjustment`; dangling `lease_id` fails every update (data corruption); tax-book download returns zero rows (open gap — join `fdh` via `distribution_source_book`). `fa_adjustment_pub.do_adjustment` defaults `transaction_subtype` to EXPENSED — set `'AMORTIZED'` when `fa_asset_val_pvt.validate_exp_after_amort(asset_id,book)` is false (Oracle rejects expensed once a prior amortized adjustment exists) or the user entered an Amortization Start Date; pass that date only when `value_modified` (the downloaded value is the LAST adjustment's date and would amortize retroactively — unmodified, FA defaults the current period). Assignment changes (expense account/location/employee) go through `fa_transfer_pub.do_transfer` on the single active distribution; rows of multi-distribution assets carry no distribution identifier, so a changed assignment there is refused. Asset key combinations are created on the fly via `fnd_flex_ext.get_ccid('OFA','KEY#',fa_system_controls.asset_key_flex_structure,...)`; the ASSET_KEY column LOV is value-only for that reason. Category-driven LIFE/PRORATE defaults are guarded with `not exists` on `fa_additions_b` so a category edit does not re-default an existing asset's life.

## MRP/MSC Sourcing Rule Assignment (`XXEN_MRP_UPLOAD`, `XXEN_MSC_UPLOAD`, + `_11I`)

`mrp_src_assignment_pub.process_assignment` on UPDATE keeps a `G_MISS` field and clears a NULL one, and rewrites every column with fresh who columns without comparing: send an unchanged set with operation `mrp_globals.g_opr_none` (no write, the id passes through) and leave an unchanged assignment out of the table. The API validates no DFF segment and stores what it is given. The MSC planning tables have no API or table handler (the forms use direct DML), so the upload merges into the fetched `%rowtype` and skips the update when nothing changed. `msc_sr_assignments.item_type_value` is NULL on form-created rows and means Usable (1): compare it as `nvl(col,1)`, like the key cursor and `msc_sr_assignments_v`. The set columns repeated on every row are applied by the first row of that set in the file only; a Delete Option 'Assignment Set' on a later row is rejected with a message, and decision: a set-level edit on a later row stays silently ignored, as in every other upload with a repeated parent.

## QA collection results (`XXEN_QA_UPLOAD.collection_result`)

- One procedure serves every collection plan: a plan's upload names each column after its element as Oracle names the `Q_<plan>_V` columns (`upper(translate(qa_chars.name,' ''*{}','_____'))`) and maps it to a typed slot (`p_char1..40`, `p_number1..20`, `p_date1..10`); the procedure reads that mapping from `xxen_upload_parameters` for `xxen_upload.run_id`. A new plan needs only an upload XML; the download and Success SQL read the plan view.
- Write through `qa_results_pub.insert_row`/`update_row` with `p_commit=>fnd_api.g_false` and `p_enabled_flag=>2`; status 1 stores a pending result that the plan views do not show. Pass `p_who_last_update_login=>fnd_global.login_id` (the default is the user id).
- The API checks a mandatory element only when it is in the element array, so an insert passes every enabled plan element; an element that is not enabled in the plan ends the call with status U and `ORA-01403`.
- `update_row` writes a `qa_results_update_history` row for every element passed, unchanged ones included: pass only values that differ from the stored ones. A dependent element (`qa_chars.dependent_element='Y'`: Lot, Revision, Serial, UOM, Locator, ...) is validated against package globals set while its parent (Item, Subinventory, ...) is validated in the same array, so a changed dependent element must travel with its parents.
- Pass dates as `'YYYY/MM/DD'` and numbers through `fnd_number.number_to_canonical`. The API rounds numbers silently to the plan or element precision and cuts text at 150 bytes without checking the display length, so text columns take `DATA_LENGTH` 150.
- The API does not check plan effective dates, collection plan security (`qa_web_txn_api.allowed_for_plan('QA_RESULTS_ENTER'|'QA_RESULTS_UPDATE',plan_id)`), e-signatures or element defaults, and leaves background actions (QLTACTWB, submitted only with `p_commit` true), sequence generation (`qa_sequence_api.generate_seq_for_txn`) and datetime timezone conversion to its other callers. The upload refuses plans with actions and with Sequence or Date and Time elements.
- `fnd_msg_pub` holds the API's errors with a `(CHAR_ID=n)` suffix; build row messages from `x_error_array` with `qa_validation_api.get_error_message` and `&CHAR_PROMPT` replaced by `qa_plan_element_api.get_prompt`. `x_message_array` is indexed from 0.
- Assign the uploads to `QARSMDF` (Enter Quality Results) and `QARSUPD` (Update Quality Results); `QARSINF` is view only.

## OKC/OKL contract records

Fields default to `OKC_API.G_MISS_*`: `G_MISS` = keep, NULL = set null. Never `rec := null` (nulls every column); a sparse record is safe; a cleared cell (`fnd_api.g_miss_num = okc_api.g_miss_num`) reads as keep — detect and refuse explicitly.
